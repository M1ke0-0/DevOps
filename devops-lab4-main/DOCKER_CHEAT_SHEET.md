# 🛡️ Шпаргалка для подготовки к защите (Docker & Compose)

Этот конспект составлен на основе твоих ответов с фокусом на те моменты, где преподаватели чаще всего «ловят» студентов.

---

## 🏗️ 1. Dockerfile: Слои и Кэширование
**Вопрос:** *Почему мы копируем `requirements.txt` отдельно от остального кода?*

*   **Ответ:** Для **оптимизации кэша**. Каждый шаг в Dockerfile — это слой.
    *   Если изменить код в `main.py`, Docker увидит, что слой с `requirements.txt` не менялся, и **пропустит** шаг `pip install`.
    *   Если скопировать всё сразу, при любом изменении кода Docker будет заново скачивать все библиотеки. Это долго и тратит трафик.

## 🚦 2. Docker Compose: `depends_on`
**Вопрос:** *Гарантирует ли `depends_on`, что бэкенд не упадет при запуске БД?*

*   **Ответ:** **НЕТ.** Он гарантирует только запуск *контейнера*. 
    *   Постгресу нужно время на инициализацию. В этот момент контейнер уже «Up», но порт еще не принимает соединения.
    *   **Решение:** Использовать `healthcheck: test: ["CMD-SHELL", "pg_isready"]` в сервисе БД и `condition: service_healthy` в `depends_on` бэкенда.

## 🔒 3. Безопасность и Root-права
**Вопрос:** *Почему плохо запускать приложение от root?*

*   **Ответ:** При взломе приложения злоумышленник получает полные права внутри контейнера и может попытаться «вырваться» на хост-машину.
*   **Как исправить:** Использовать инструкцию `USER` в Dockerfile.
    ```dockerfile
    RUN useradd -m myuser
    USER myuser
    ```

## 🛑 4. Завершение работы: Exec vs Shell form
**Вопрос:** *В чем разница между `CMD python main.py` и `CMD ["python", "main.py"]`?*

*   **Shell form (`CMD python ...`):** Docker запускает `/bin/sh -c`, который запускает Python. Сигнал остановки (**SIGTERM**) приходит оболочке, а она не передает его Python-у. Приложение убивается «грязно» через 10 секунд.
*   **Exec form (`CMD ["python", "main.py"]`):** Python запускается как **PID 1**. Он сразу получает сигнал остановки и может корректно закрыть соединения (Graceful Shutdown). **Это стандарт.**

---

## 🧹 5. Эксплуатация: `stop` vs `down`
**Вопрос:** *Что произойдет, если выполнить `docker-compose down`?*

*   **stop:** Просто останавливает процессы. Контейнеры и сети остаются на месте в состоянии "Exited".
*   **down:** Останавливает и **удаляет** контейнеры и виртуальные сети.
    *   *Важно:* Данные в **Volumes** (томах) сохраняются, если не добавить флаг `-v`.

---

## 💾 6. Volumes: Bind vs Named
**Вопрос:** *В чем разница между `./data:/var/lib/data` и `my_data:/var/lib/data`?*

*   **Bind Mount (`./path`):** Это прямая ссылка на папку на твоем диске. Удобно для разработки (правишь код — он меняется в контейнере).
*   **Named Volume (`my_data`):** Управляется Docker-ом. Ты не знаешь точно, где лежат файлы (обычно в недрах `/var/lib/docker/`). Это быстрее и безопаснее для баз данных в продакшене.

## 🚀 7. Жизненный цикл (Cheat-команды)
*   **`docker-compose up -d --build`** — собрать образы заново и запустить все в фоне.
*   **`docker-compose exec <service_name> bash`** — зайти внутрь работающего контейнера.
*   **`docker-compose logs -f`** — смотреть логи в реальном времени.
*   **`docker system prune`** — очистить весь неиспользуемый «мусор» (образы, сети).

### 💡 Самые важные слова для защиты:

3.  **Оркестрация** (управление группой контейнеров как единым целым).
